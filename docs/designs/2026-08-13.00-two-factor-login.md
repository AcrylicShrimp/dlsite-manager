# Two-Factor (TOTP) Login

## Observed DLsite Contract

DLsite does not document its two-factor flow, so it was captured live with
`cargo run -p dm-api --example probe_login` against a two-factor-enabled account:

- The credential POST to `https://login.dlsite.com/login` returns `302` to
  `https://login.dlsite.com/login/two-factor`.
- A wrong password *also* returns `302`, back to `/login`. The redirect target, not the POST
  status, is what identifies a challenge.
- The challenge page renders one form:
  - `action="https://login.dlsite.com/login/two-factor?user=self"`, method `POST`
  - `_token` — hidden, per-session Laravel CSRF token
  - `otp` — the verification code, `type="text"`, `required`
  - `save_id` — unchecked checkbox
  - `recaptcha_token` — hidden, populated by reCAPTCHA v3 in the browser
- The page is served by viviON ID and mentions Google Authenticator explicitly.

`dm-api` replays that form as rendered — every non-code control that a browser would submit,
with `otp` filled in — rather than hardcoding a field list. Values are carried verbatim, so
the per-session `_token` survives. The submission therefore matches a browser's apart from
one thing:

**reCAPTCHA v3 is submitted empty.** The page's JavaScript fills `recaptcha_token` with a
score token refreshed every 60 seconds, which a plain HTTP client cannot produce. Whether
DLsite enforces the token server-side is unknown; if it does, the code submission will be
refused and this design needs a webview-based login instead. This is the single largest
risk in the feature and must be checked during live verification.

A rejected code is detected structurally, without depending on DLsite's error wording: the
response either redirects back to `/login/two-factor` or re-renders a page that still parses
as a challenge.

## Session Persistence

Login happens inside every sync and every download job, and TOTP codes are single-use, so
without session reuse a two-factor account would face a dialog per job — including one per
queued download. Sessions are therefore persisted, but only for accounts that already keep
their password.

They are stored through `dm-credentials` under `CredentialRef::account_session(account_id)`
(`account:{id}:session`), the same store that holds account passwords. A DLsite session
cookie grants the access a password grants, so it belongs at the same storage level rather
than in the library database. The store is a permission-restricted local JSON file; this is
the existing storage posture for secrets in this app, not a new one.

`Library::authenticate_account` is the single entry point for both sync and download:

1. restore the stored session and check it with `validate_session`; if it holds, done;
2. otherwise discard it and log in with the password;
3. if DLsite answers with a challenge, ask the UI for a code, up to three attempts;
4. persist the resulting session, if the account remembers its password.

The session follows the account's `remember_password` setting, which is visible on the
account as an absent `credential_ref`. An account that does not keep its password does not
keep a session either, and any session stored before that setting changed is dropped on the
next login. Such an account therefore answers a prompt per job, which is the cost of the
setting rather than a defect.

Stored sessions are also dropped when an account is removed, and when `save_account` changes
the login name or supplies a new password.

## Serializing Logins Per Account

`Library` holds one `tokio::sync::Mutex` per account ID, held for the duration of
`authenticate_account`. Without it, jobs started together would each begin their own login
and each raise its own dialog. With it, the first login stores a session that the others then
restore. A job waiting on this lock polls its cancellation token while it waits, so a job
queued behind another job's open dialog still aborts on Cancel instead of waiting out that
dialog's five-minute timeout.

## Job-to-UI Prompt Channel

Background jobs cannot show UI, so `dm-library` takes a `TwoFactorPrompt` through the sync and
download request structs and `src-tauri` implements it:

- the job registers a `oneshot` channel keyed by a request ID and emits
  `dm-two-factor-request` with the account, the attempt number, and whether the previous code
  was rejected;
- the frontend queues requests, shows `TwoFactorDialog.svelte` for the head of the queue, and
  answers with `submit_two_factor_code` or `cancel_two_factor`;
- the job waits on the channel, the job's cancellation token, and a five-minute timeout,
  whichever comes first, then emits `dm-two-factor-closed` so the dialog comes down in every
  case.

The prompt reports which of those happened as a `TwoFactorPromptResponse`, because the two
non-answers mean different things to the job. Dismissing the dialog or cancelling the job
raises `LibraryError::TwoFactorCancelled`, whose failure code is the plain `cancelled` that
`dm-jobs` recognizes, so the job finishes as Cancelled; its `failureKind` detail still reads
`two_factor_cancelled` for the UI. Letting the prompt expire raises
`LibraryError::TwoFactorTimedOut` and fails the job, since nobody chose that outcome.

Verification codes are never logged or audited. Audit events record only that a code was
submitted or that verification was cancelled, keyed by request ID.
