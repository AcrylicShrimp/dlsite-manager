# Manual Auto-Update

## Status

Accepted and first implementation in progress.

## Direction

`dlsite-manager` uses the Tauri 2 updater plugin with GitHub Releases as a static update host. The app does not run startup update checks. Users explicitly start the flow from Settings.

## Release Hosting

Stable builds read:

`https://github.com/AcrylicShrimp/dlsite-manager/releases/latest/download/latest.json`

The release workflow creates updater artifacts and uploads `latest.json` alongside the normal installers. Stable releases are still created as drafts first, so update discovery starts only after the release is manually published. Prerelease/RC tags may upload updater metadata, but the committed stable endpoint follows GitHub's latest non-prerelease release.

Windows builds retain both MSI and NSIS installers, including release candidates.
WiX/MSI rejects the alphabetic `rc.N` prerelease identifier, so the release build passes
a narrow `bundle.windows.wix.version` override: app/tag `3.3.0-rc.1` maps to MSI
`3.3.0.1`. The app version, installer filename, and updater metadata retain `3.3.0-rc.1`.
The workflow checks MSI limits (255/255/65535/65535) before invoking the build.
Stable versions use Tauri's normal conversion. The updater continues to select NSIS.

Windows Installer compares only the first three numeric fields, so the fourth field
does not enforce RC ordering. Tauri CLI 2.11.4's default WiX template handles replacing
related versions with the existing `allowDowngrades = true` default (or
`AllowSameVersionUpgrades` when downgrades are disabled); the upgrade code is unchanged.
Do not claim strict MSI RC-versus-stable ordering from the fourth field. Actual
RC-to-stable installer replacement remains part of native acceptance.

For workflow-only release repairs, dispatch the corrected workflow from `release` with
the existing tag input; build checkout still uses the original immutable tagged source.

## Linux AppImage packaging

Use Tauri CLI 2.12.0 or later to build new AppImages. Its bundled packaging tool
includes [Tauri #15804](https://github.com/tauri-apps/tauri/pull/15804), which stops
including xdg-open and xdg-utils and relies on the desktop host's utilities instead.
This is a build-tool change; updating the Rust runtime or opener plugin alone does
not change the bundled files. Existing published AppImages need a new build to
benefit from it.

For [folder-opening issue #47](https://github.com/AcrylicShrimp/dlsite-manager/issues/47),
prefer rebuilding with the upstream fix and verifying downloaded folders, log folders,
Unicode/space paths, and external links on the reporter's Linux desktop before adding
a custom opener. The upstream change does not establish that inherited AppImage
environment-variable conflicts are fixed. Per the maintainer's 2026-09-27 request,
close #47 after publishing 3.3.0 and ask the reporter to report any remaining failures;
closing the issue does not establish Linux desktop acceptance.
The existing Wayland-library repack and final-artifact signing still apply.

## Signing

Tauri updater artifacts are signed separately from OS code signing. The updater public key is committed in `src-tauri/tauri.conf.json`; the private key must remain outside the repository and be provided to release builds through GitHub Actions secrets.

Required release secret:

- `TAURI_SIGNING_PRIVATE_KEY`

Optional release secret:

- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`

The first generated maintainer-local key path is `~/.tauri/dlsite-manager.key`. Losing this private key prevents publishing future updates to already-installed updater-capable builds.

Release automation expects `TAURI_SIGNING_PRIVATE_KEY` to contain the private key file contents, not a repository path. For a local signed bundle, load the file content into the environment and set `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` explicitly, even if it is empty.

With CLI 2.12.0, `tauri build` binds updater signatures to the app version. The Linux
post-repack signing step must also pass `--app-version` using the validated release
version so its final signature carries the same authenticated version metadata.

## UI Behavior

Settings exposes a manual `Check for Updates` button in the About panel. Pressing it checks the configured endpoint, downloads and installs an available update, then relaunches the app. If no update exists, the user sees a toast and no background polling is scheduled.

The Tauri-specific updater and process calls stay behind `src/lib/api/native.ts`, which normalizes download progress for the route. The route owns update lifecycle state, toast policy, and relaunch consequences. `SettingsView.svelte` composes the presentation-only `UpdatePanel.svelte`; the reusable panel has isolated Storybook states for idle, checking, downloading, and installing behavior.

## Known Constraints

- Builds before this feature cannot auto-update themselves.
- The first updater-capable release can only update to later releases.
- Current release automation publishes Apple Silicon macOS and Windows x64 updater entries.
- Updater signing does not replace Apple notarization or Windows code signing.
- macOS builds use ad-hoc app-bundle signing (`bundle.macOS.signingIdentity = "-"`) so bundle resources are sealed and updater tarballs/DMGs are structurally valid. This still does not satisfy Gatekeeper for normal quarantined downloads; Developer ID signing plus Apple notarization is required for that.
