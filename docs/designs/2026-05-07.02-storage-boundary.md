# Storage Boundary

## Decision

Use a dedicated `dm-storage` crate backed by SQLite through SQLx.

`sqlx 0.9.0-alpha.1` is used because it is the newest crate version currently reported by Cargo. Keep the first storage slice conservative until that dependency choice has more mileage in the project.

The first cut was intentionally small:

- open or create a SQLite database;
- run embedded SQLx migrations;
- expose an explicit write transaction wrapper;
- add only settings needed by the first GUI slice.

The product-list cache includes account/ownership tables and `work_downloads` for durable
content state. Serial values deliberately remain outside SQLite.

## Transaction Rule

All write operations must be enclosed within a transaction.

Storage APIs should preserve that rule structurally:

- migrations use SQLx's migration runner, where normal migrations are transactional by default;
- public mutation APIs should either open their own transaction for one logical write or accept a `WriteTransaction`;
- future multi-step write workflows should start one transaction at the service boundary and pass the transaction through repository methods;
- `dm-storage` must not expose its raw SQLx pool or connection as public API, because callers could otherwise bypass the transaction rule.

## Current Surface

`Storage` owns the SQLite pool and exposes:

- `open(path)` for file-backed databases;
- `open_in_memory()` for tests;
- `run_migrations()`;
- `begin_write()`.
- `app_settings()`;
- `save_app_settings()`.
- `accounts()`;
- `save_account()`;
- `set_account_enabled()`;
- `record_account_login()`;
- `commit_account_sync()`;
- `record_sync_failure()`;
- `record_sync_cancellation()`;
- `sync_runs_for_account()`;
- `list_products()`.

`WriteTransaction` still exposes the minimal static SQL execution hook used by tests, but it now also exposes account/cache write methods for multi-step service operations:

- `upsert_account()`;
- `set_account_enabled()`;
- `record_account_login()`;
- `commit_account_sync()`;
- `record_sync_failure()`.
- `record_sync_cancellation()`.

The account sync write is intentionally atomic: one transaction records the sync run, upserts work details, upserts account ownership, marks missing ownership stale, and updates account sync metadata.

The initial `app_settings` table stores:

- `library_root`;
- `download_root`.

Both settings are nullable at the domain level. Missing values are represented by absent key/value rows.

`library_root` is the final managed library location after download and unpacking. `download_root` is a download staging location, not the final library: it holds partial downloads, retry/resume state, and fetched archives before they are moved or unpacked. The GUI labels this as the download staging folder and defaults it to the platform Downloads directory when no saved value exists.

The product-list cache stores:

- `accounts` for local DLsite account/source metadata, including non-secret `credential_ref`;
- `works` for global cached work details keyed by `work_id`;
- `account_works` for account-specific ownership and purchase timestamps;
- `sync_runs` for completed/failed sync attempts and cache reconciliation.

`accounts.credential_ref` points to `dm-credentials`; passwords are not stored in SQLite.

## Tauri Adapter

The current Tauri adapter initializes `dm-storage` in app setup using the platform app data directory and runs migrations before command registration.

Current commands:

- `get_settings`;
- `save_settings`.
- `list_accounts`;
- `save_account`;
- `set_account_enabled`;
- `list_products`;
- `start_account_sync`;
- `list_jobs`;
- `get_job`;
- `cancel_job`;
- `get_job_logs`;
- `clear_finished_jobs`.

These commands validate/normalize string input, call `dm-storage`, `dm-library`, or `dm-jobs`, and translate errors. They do not own SQL or schema details.

## Download recovery and secrets

`download_finalizations` stores one bounded operation per work: operation identity, canonical
source/final/previous/temporary paths, and a committed flag. `begin_download_finalization`
persists intent before preparation. `commit_download_finalization` writes the new download
row and committed marker in the same transaction, rejecting an absent/mismatched operation.
`clear_download_finalization` removes only the matching operation after recovery/cleanup.
Filesystem state is never inferred solely from the marker: Library checks owned paths too.

Replacement keeps an existing downloaded content state unchanged until finalization commits.
Only its operational `staging_path` may change before transfer or after rollback, so retained
staging remains discoverable for later deletion. Recovery intent is not cleared until that
path is durably tracked; conflicting existing staging is preserved unless deletion was requested.
Generic
jobs describe the attempt/progress; the row describes content. A completed update can be
converted directly to `WorkDownloadState`, avoiding a fallible read after a successful commit.
Fresh-download failure/cancellation recording remains supported.

Passwords and remembered session snapshots live in `dm-credentials`, not SQLite. Serial
values live only in their managed content files. Generic job history remains process-local.

## Isolated release verification

The optional `src-tauri/tauri.qa.conf.json` build override uses a different application
identifier, which separates Tauri's app-data database, credential vault, and logs from the
normal app. QA updater endpoints/artifacts are disabled. It does not isolate user-selected
library/staging roots; QA must use disposable folders or a correctly rebased backup copy.
Normal/release builds do not load this override unless explicitly passed with `--config`.

The file-backed v3.2.2 upgrade regression runs the original five embedded migrations,
preserves their checksum history, populates representative state, then reopens and runs
the current migrator twice. It verifies old data and SQLite integrity as well as the new
recovery table. This complements, but does not replace, rehearsal with a real backup copy.
