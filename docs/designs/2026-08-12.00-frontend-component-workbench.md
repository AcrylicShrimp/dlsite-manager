# Frontend Component Workbench

## Decision

Use Storybook with the official `@storybook/sveltekit` framework as the isolated component
workbench for the frontend refactor and visual-polish work.

Storybook complements the Tauri application; it does not replace Tauri runtime smoke testing.
Components that depend on native commands should be split so display state is supplied through
plain props and user intent is returned through callbacks. Stories then render those display
components with deterministic fixtures rather than contacting Tauri.

## Shared Theme Boundary

Application-wide color, typography, reset, and focus tokens live in
`src/lib/styles/theme.css`. The SvelteKit root layout and Storybook preview both import this file,
so component stories and the packaged app use the same visual foundation.

Page-specific layout remains scoped to page or feature components. In particular, the Tauri app's
full-height and overflow rules stay with the app page rather than becoming Storybook defaults.

## Story Shape

The first story set covers:

- primary, secondary, danger, compact, and disabled button states;
- normal, search, and disabled fields;
- success, information, error, and long-message toasts;
- normal and destructive confirmation dialogs;
- one component-foundations overview for shared tokens and controls.

The shell story set covers the shared app frame, selected navigation state, workspace title hierarchy,
interactive view switching, and desktop/narrow navigation layouts. `AppShell` owns only the frame
and view-to-title copy; the route remains the owner of active view state and feature content.

Library Product Card stories use synthetic metadata and an inline generated thumbnail. They cover
owned, local-only, downloaded, and active-download states while callbacks report interactions in the
story harness instead of invoking Tauri or the system clipboard.

Library Controls stories cover ready, expanded-filter, and busy states. `LibraryControls` owns the
sticky search/action layout, search text binding, and accessible filter disclosure; the route keeps
query execution, filter data, and sync/download job orchestration. Its story harness renders only a
small filter placeholder so the shell can be reviewed before `LibraryFilters` is extracted.

Library Filters stories cover neutral and populated selections with deterministic account, maker,
and custom-tag facets. The interactive harness exercises single/multi-select controls and the
include/exclude/clear custom-tag cycle without issuing cache queries. Long labels and facet counts
are included so desktop wrapping and the phone two-column chip layout can be reviewed directly.

Product Action Menu stories cover not-downloaded, downloaded, failed-record, and active-job states.
The component determines which menu items are visible from download status and reports actions or
Escape dismissal through callbacks; the route keeps anchor geometry, confirmations, file dialogs,
and download mutations.

Product Image Preview stories render a synthetic landscape image with normal and long titles. The
component owns modal/backdrop structure, contain sizing, accessible image text, and responsive panel
spacing while returning close intent from backdrop, button, or Escape interaction.

Bulk Download Dialog stories cover confirmation, partial planning failure, and nothing-to-download
notice states. The component receives a deterministic backend preview, formats known/unknown expected
bytes with the production helper, and reports cancel/confirm intent without starting jobs.

Product Detail Dialog stories cover downloaded multi-account ownership, local-only sparse metadata,
and failed-download diagnostics. The production component owns modal layout, type-tone presentation,
derived display formatting, custom-tag input, and accessible close/preview/copy controls. Story
callbacks expose intent without using the clipboard, system opener, Tauri commands, or persisted tags.

Library View stories exercise the complete composition with populated, filters-open, loading, and
empty states. `LibraryView` composes controls, filters, pagination, and product cards while receiving
all query/job projections and effects from the route. This is the acceptance surface for Library
density and responsive behavior; narrower component stories remain useful for focused state review.

Downloads View stories cover active, loading, and empty queue states, with a focused Queue Row story
for terminal failure presentation. `DownloadsView` owns the page shell and queue summary, while
`DownloadQueueRow` owns kind/status/progress/time/cancel presentation. The route remains responsible
for selecting active download jobs and projecting product-aware titles and job details, so stories
use deterministic fixtures and callbacks without changing the live-queue-only application contract.

Accounts View stories cover populated, loading, and empty source lists. Focused Source Row stories
cover selected, actively syncing, and disabled accounts, while Account Editor stories cover new,
editing, and saving states. The components own summary, status, responsive list/editor layout, and
bound input presentation; account persistence, removal confirmation, enabled mutations, and job
orchestration stay in the route and are represented by callbacks in the workbench.

Activity View stories cover populated, loading, empty, and unavailable-log-directory states. The
view composes separate recent-job and audit-log lists, preserving independent desktop scroll panes
and switching to document-flow panels on phones. Job/account projections, recent-item selection,
clearing, cancellation, directory opening, and reload effects stay route-owned behind callbacks.

Settings View stories cover ready, native-data loading, and saving states. The component composes
shared fields, text inputs, and buttons for the storage-path form and projects deterministic About
metadata without Tauri. Directory dialogs, settings persistence, default-path lookup, and external
links remain route-owned callbacks; narrow stories verify stacked controls and truncated long values.

Small story-only Svelte harnesses are acceptable when a production component uses snippets or
bound state that is awkward to express as serializable Storybook args. Harnesses must compose the
real production component and must not duplicate its styling.

## Native Command Boundary

Application-specific Tauri commands are exposed through thin typed functions in
`src/lib/api/tauri.ts`. This module owns command names, top-level request envelopes, and response
types; feature components continue to receive plain data and callbacks and do not import Tauri.

The wrapper does not translate errors, cache data, or hide job lifecycle behavior. Loading state,
toasts, confirmations, event-driven job updates, and follow-up reloads remain explicit in the route
until a feature has enough cohesive orchestration to justify a small controller. Generic Tauri app,
event, path, dialog, and opener APIs remain separate from application command wrappers behind
`src/lib/api/native.ts`, keeping Tauri package imports out of the route and feature components.

## State Orchestration Boundary

`src/lib/controllers/job-controller.svelte.ts` owns the one cross-view state stream: job snapshots,
job loading state, transient job messages, and native job-event subscription/merge behavior. The
route explicitly handles terminal-event consequences such as reloading accounts, products, and
audit events or projecting completed downloads into the current product data.

Library queries, account editing, audit loading, and settings forms remain route-owned because each
currently has one straightforward caller and one display component. Introducing controllers for
those flows would add indirection without creating a reusable boundary. They should move only if a
second consumer or independently testable workflow appears.

As feature components are extracted, their stories should cover meaningful state differences such
as empty/loading/error, long content, disabled actions, active progress, and narrow layouts. Tauri
modules may be mocked only at a narrow adapter boundary when a plain fixture/callback component is
not sufficient.

## Validation

Frontend component slices use:

- `pnpm check` for Svelte and TypeScript diagnostics;
- `pnpm build` for the packaged frontend;
- `pnpm build-storybook` for the isolated component bundle;
- browser inspection of affected stories at the default desktop viewport and applicable narrow
  breakpoints;
- `git diff --check` for patch hygiene.

Storybook build output is generated under `storybook-static/` and is not tracked. The workbench is
local development tooling and is not included in Tauri release artifacts.
