# Frontend Component Workbench

## Decision

Use Storybook with the official `@storybook/sveltekit` framework as the isolated component
workbench for the frontend refactor and visual-polish work.

Storybook complements the Tauri application; it does not replace Tauri runtime smoke testing.
Components that depend on native commands should be split so display state is supplied through
plain props and user intent is returned through callbacks. Stories then render those display
components with deterministic fixtures rather than contacting Tauri.

## Shared Theme Boundary

Application-wide color, typography, reset, and focus tokens live in
`src/lib/styles/theme.css`. The SvelteKit root layout and Storybook preview both import this file,
so component stories and the packaged app use the same visual foundation.

Page-specific layout remains scoped to page or feature components. In particular, the Tauri app's
full-height and overflow rules stay with the app page rather than becoming Storybook defaults.

## Story Shape

The first story set covers:

- primary, secondary, danger, compact, and disabled button states;
- normal, search, and disabled fields;
- success, information, error, and long-message toasts;
- normal and destructive confirmation dialogs;
- one component-foundations overview for shared tokens and controls.

The shell story set covers the shared app frame, selected navigation state, workspace title hierarchy,
interactive view switching, and desktop/narrow navigation layouts. `AppShell` owns only the frame
and view-to-title copy; the route remains the owner of active view state and feature content.

Small story-only Svelte harnesses are acceptable when a production component uses snippets or
bound state that is awkward to express as serializable Storybook args. Harnesses must compose the
real production component and must not duplicate its styling.

As feature components are extracted, their stories should cover meaningful state differences such
as empty/loading/error, long content, disabled actions, active progress, and narrow layouts. Tauri
modules may be mocked only at a narrow adapter boundary when a plain fixture/callback component is
not sufficient.

## Validation

Frontend component slices use:

- `pnpm check` for Svelte and TypeScript diagnostics;
- `pnpm build` for the packaged frontend;
- `pnpm build-storybook` for the isolated component bundle;
- browser inspection of affected stories at the default desktop viewport and applicable narrow
  breakpoints;
- `git diff --check` for patch hygiene.

Storybook build output is generated under `storybook-static/` and is not tracked. The workbench is
local development tooling and is not included in Tauri release artifacts.
