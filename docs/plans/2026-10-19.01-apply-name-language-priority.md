## Goal and Scope

Persist one ordered language preference for both work titles and maker names, then apply it consistently to list/detail display, title sorting, maker facets, and bulk selection. The preference accepts language codes beyond the five currently named in the API model. Keep searching **all** stored language values regardless of priority. Expose the setting through existing Tauri settings commands and expose the language codes present in cached names for the dependent editor. This step establishes the backend contract and updates the existing maker-filter UI to that contract; the preference editor itself is a dependent step.

## Proposed Changes

Store language-code order as one app setting, using the existing `app_settings` key-value table. The default list copies the current English-first selector's five named cases; it is not a claim about every language DLsite may return. A stored preference is an ordered list of unique, nonblank codes, not a permutation of those five cases. Do not impose a fixed list/code length cap: every discovered code must remain eligible, including when the number of observed codes grows. Pass the entire priority as one bound JSON array to SQL and rank matching keys through `json_each` rather than expanding one parameter or expression per code. This keeps SQL shape stable as codes are added and never interpolates a code into SQL text. A code absent from the list remains searchable and is chosen only after configured codes, with remaining keys ordered deterministically by code. Do not infer a work's actual source language from the API; here “Japanese first” means `ja_JP` first when that value exists. Preserve the user's agreed scope: the same ordered list applies to both fields.

`dm-storage` owns validation, selection and SQL projection. A settings patch validates supplied priority before writing, then reads the previous value and writes paths/priority in one transaction; omitting priority keeps that value. An absent key means the default order. A malformed stored priority returns `InvalidStoredValue` instead of silently resetting it; a supplied valid full priority can replace a malformed value. `dm-library` reads the saved setting at the start of each library operation and passes a resolved snapshot into storage queries; a multi-page bulk selection must reuse one snapshot across pages so a mid-job settings save cannot change its sort order. The selected title must be computed in SQL *before* `LIMIT/OFFSET`; applying the preference to only returned rows would break paging and sort. A query for `ja_JP` should fall back through the rest of the ordered list, then unknown keys; an empty string is never a selected name. Search uses all JSON values and remains independent of this setting.

The current Tauri `bulk_download_candidates` helper also pages by repeatedly calling `Library::list_products`, so it would re-read preference on every page. Move that candidate-selection loop into `dm-library` as a public core operation reusing its existing paginated selection path and one resolved query snapshot; Tauri preview/start commands call it once and retain their reservation/job adapter roles. Deduplicate work IDs as the existing helper does. Keep the later preview/download core selection snapshot stable as well. A preference save between pages must not change the candidate set.

For maker facets, return `{ key, name, count }` where `key` uses a nonblank, trimmed `maker_id` when present, otherwise a fixed English-first fallback of `maker_json`, with disjoint prefixes. Group/count by key and choose a deterministic label from the group using current preference. A missing maker has no facet. This preserves a selected filter across priority changes while showing the new language label. Include the maker-key contract in the existing bulk preview/download query path, not just the visible page.

Update `docs/designs/2026-05-09.00-unified-product-list-and-accounts.md` at implementation time to record JSON as the name source, configurable selection, all-language search, stable maker filter keys, and the remaining performance tradeoff. Do not alter historical migration files.

Add a storage query for distinct name-language keys from nonempty string values in either JSON map, followed by a thin library/Tauri read command. Include all cached works, independent of ownership filter, because the preference is global. This discovery supports the editor without limiting the preference model: already saved codes remain valid even when no cached work currently uses them.
