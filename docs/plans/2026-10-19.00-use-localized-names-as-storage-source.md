## Goal and Scope

Make `works.title_json` and `works.maker_json` the only persisted work/maker name sources. Remove the preselected `works.title` and `works.maker_name` columns without losing existing names or changing the current English-first display default. Search work and maker names across **every nonempty language value**, independently of display choice. This is a storage/domain change; configurable priority and UI are dependent plans.

## Proposed Changes

The old schema deliberately duplicated selected names for display and query convenience. The agreed preference feature makes that selection dependent on user settings, so retaining it as a stored source would allow conflicting values. Keep the localized JSON columns, not `raw_json`, as the name contract. `dm-storage` owns JSON selection and SQL search; `dm-library` writes the normalized map or single-value placeholder. Keep DTO `title`/`maker_name` fields as computed output, not persisted fields.

Use the existing fallback order (`en_US`, `ja_JP`, `ko_KR`, `zh_TW`, `zh_CN`, then other codes in deterministic code order) until the next plan adds a stored preference. These five are the current parser's named cases, not a verified exhaustive set of DLsite languages. Trim empty values before selection. On upgrade, if a row's JSON is not a usable object with any nonempty string, preserve its old selected title/maker in an `und` entry; title ultimately falls back to `work_id`. Do not label an unknown legacy string as Japanese. Existing populated JSON must retain every language entry. Guard JSON iteration against malformed legacy values. Existing SQLite plain indexes on `title`/`maker_name` are dropped with the columns; measure query behavior on a representative library rather than assuming those indexes previously accelerated `lower(title)` or `%term%` searches.

The migration must use a compatible column-removal approach for the SQLite runtime used by `sqlx`; check the runtime version and dependent schema before choosing `ALTER TABLE ... DROP COLUMN` or a transactional rebuild. Preserve foreign-key relationships and rollback safety. Change the old design document's storage/search statements when this implementation executes; keep the prior rationale as historical context.
