# Fix post-merge bugs and clarify authentication boundaries

- State: Implemented; manual/native and live verification pending

- Scope: offline bug fixes and internal refactoring implemented; no real-account login or

## Objective

Make two-factor cancellation consistent across sync, single downloads, bulk downloads,
durable records, and the UI. Protect existing downloaded files during replacement failures,
and prevent stale Library requests from overwriting the current selection.

Refactor the internal boundaries needed to test and maintain these behaviors. Keep the
existing crate responsibilities and avoid a repository-wide restructuring.

## Evidence and scope

| Finding | Current behavior | Required outcome |
| --- | --- | --- |
| Two-factor cancellation classification | `LibraryError::TwoFactorCancelled` has failure code `cancelled`, but sync persistence, download persistence, and the bulk loop match other enum variants directly. | One semantic cancellation predicate governs every consumer; prompt cancellation stops the owning operation and is recorded consistently. |
| Bulk cancellation results | The bulk loop returns a bare error on cancellation, dropping its accumulated report before Tauri can project completed works. | Preserve completed work results, prior failures, and the interrupted work when stopping; untouched works remain untouched. |
| Replacement failure | `download_work_inner` removes the old final directory before `move_downloaded_work_dir`; its copy fallback writes directly to the final name. | Prepare a complete payload on the destination filesystem before replacing anything; preserve rollback material through the durable state update. |
| Stale Library requests | `loadProducts` and facet loading write shared state without checking which request is current; filters remain interactive during loading. | Only the latest query generation can update products, facets, pagination, loading, or query errors. |

Cancellation failures were reproduced with failing tests before behavior changes. The fixed
implementation now has deterministic filesystem failure/restart and frontend race coverage;
those filesystem/frontend tests were not run on the pre-fix baseline. Native GUI verification
remains separate from controller/adapter tests.

Two-factor reCAPTCHA enforcement remains an **unverified external contract**, not a confirmed
bug. Track live validation separately below. Plaintext vault policy, CSP, toolchain pinning,
archive-engine redesign, and unrelated component cleanup are outside this implementation.

## Internal boundaries

These boundaries were implemented; the design notes record the exact guarantees and limits.

- `dm-library/src/auth.rs`: move `DlsiteAuthSource`, prompt request/response types,
  session restore/login/challenge handling, per-account login locking, and session
  invalidation helpers into one focused module. Keep `Library::authenticate_account`
  as the shared entry point for sync and downloads. Existing public types may be re-exported
  from the crate root so the mechanical move does not require unrelated caller edits.
- `LibraryError::is_cancelled()`: classify ordinary cancellation, download cancellation,
  and two-factor cancellation in one place. Timeouts and rejected codes remain failures.
  Derive the exported failure code from the same classification and preserve diagnostic
  details when adapting it to `JobFailure`.
- `src-tauri/src/two_factor.rs`: isolate the prompt registry, oneshot lifecycle, request/closed
  events, and timeout/cancellation wait. Tauri remains responsible for UI communication;
  DLsite authentication and session policy remain in `dm-library`/`dm-api`.
- `src/lib/controllers/two-factor-controller.svelte.ts`: own prompt queue and request-scoped
  submitting state, with cleanup when native subscriptions end. Use existing API wrappers
  and keep `TwoFactorDialog` presentational. Late replies for an old request must not alter
  the next request's state. This extraction is justified by the independent async lifecycle.
- `dm-library/src/finalization.rs`: own narrowly scoped preparation, installation, rollback,
  and cleanup of downloaded directories. `Library` orchestrates the SQLite update between
  installation and cleanup; the filesystem helper does not own SQL or Tauri events.
- Library query orchestration: extract a small independently testable controller if needed
  for the deferred-response tests. Otherwise retain route ownership and a local generation
  counter. No generic request/cache framework or global state container is needed.

Use the existing cancellation tokens for this work. A token-library migration, generic
workflow engine, new authentication crate, and speculative webview login are unnecessary.

## Implementation sequence

### 1. Reproduce cancellation failures and extract authentication code

First add regression cases that check observable results, not only the returned error code:

- cancelling a sync's two-factor prompt records `sync_runs.status = cancelled`;
- cancelling a fresh download's prompt records cancellation and transfers no bytes;
- cancelling a bulk prompt stops before selecting/authenticating/downloading another work;
- already completed works survive bulk cancellation and remain correctly projected in the UI;
- prompt timeout and exhausted code retries still report failure, not cancellation.

Separate the mechanical `auth.rs` and Tauri prompt module extraction from the behavior fix.
Retain the current source traits for fake authentication and download sources. Group the
existing authentication tests with the new module when doing so improves navigation.

### 2. Unify cancellation and make the 2FA lifecycle testable

Replace duplicated cancellation matches in domain recording, bulk orchestration, and Tauri
error adaptation with the shared predicate. Preserve `failureKind: two_factor_cancelled`
and the account ID while keeping the generic job failure code `cancelled`.

Represent an interrupted bulk operation with a small typed error carrying its cause and
partial report, rather than dropping the report or embedding frontend JSON in the core.
Tauri can serialize this into the existing `error.details.bulkDownload` envelope. Include
enough per-work status to distinguish earlier failures from the work cancelled now; the
frontend must not mark every previous failure as cancelled merely because the parent job is.
Works not started must not receive synthetic failed/cancelled download records.

Cancellation is scoped to the requesting job. Cancelling one prompt must not cancel other
jobs/accounts. A cancelled bulk prompt stops that bulk operation, even though dismissing a
dialog does not currently flip the job token. Timeout keeps the existing per-work failure
policy; do not silently redefine timeout as cancellation or change all bulk failure handling.

Add focused authentication lifecycle coverage:

- simultaneous sync/download authentication for the same remembered account produces one
  successful login, then session reuse; waiting jobs remain cancellable;
- cancellation while session validation, password login, or code submission is awaiting
  HTTP must finish without waiting for that response and release the per-account lock;
- cancellation, timeout, rejection/retry, and success each close the corresponding prompt;
- late submit/close events cannot dismiss a newer prompt or clear its submitting state;
- valid, expired, and malformed stored sessions; network failure while validating a session
  must not be mistaken for an invalid password or discard a potentially valid session;
- non-2FA accounts, restart/session reuse, password/login-name changes, and account removal;
- remembered-session policy and account isolation when a bulk source switches accounts.

The last two groups audit the refactor's invariants; do not label every case an existing bug
without a failing reproduction. If account edits can race authentication and persist an old
session, coordinate mutation/invalidation with the account auth lock and re-read identity
under that lock. Do not introduce a global login lock or share cookie jars across accounts.

Thread the existing job token through the full authentication flow. Race network waits
against the existing cancellation polling helper, then check cancellation before retrying,
opening another prompt, or persisting a newly obtained session. Drop the pending request
future on cancellation; do not leave detached authentication work holding the lock. This
stops local waiting, not an already submitted server-side request. Audit drop safety and
keep prompt registry removal/closed-event cleanup guaranteed if its wait is interrupted.
Do not wrap filesystem swaps or SQLite commits in this cancellable network helper.
Use never-resolving fake sources at each HTTP boundary and controlled time to assert
cancellation within the existing polling interval plus scheduler allowance, lock release,
progress of the next same-account authentication, and no extra prompt/retry/session save.

Existing downloaded content needs special treatment: an authentication failure or cancellation
during replacement must keep the previous usable download state. The job describes the failed
attempt; the durable work record describes the content still on disk. Complete this guarantee
with the finalization changes in step 3.

Apply that distinction to single and bulk terminal-job handling in the frontend. Use job
results for attempt reporting, but re-query authoritative product download state for the
list and any open matching detail view instead of synthesizing content state from job
status. Route these refreshes through step 4's invalidation rules. A failed refresh must
retain the last known content state and show a refresh error, not invent failed content.
Test replacement authentication failure/cancellation with existing content: its downloaded
status, local path, completion time, and open-folder action remain available in list/detail,
while the failed/cancelled attempt remains visible in Activity. Fresh downloads must still
reflect their own persisted failure/cancellation; do not suppress those terminal states.

### 3. Make download finalization recoverable

Use a bounded per-work finalization sequence, not a claim of an atomic transaction spanning
SQLite and the filesystem:

Before authentication or any attempt-state write, read the existing download record under
the shared per-work mutation guard described below. For replacement of usable content, keep that record
unchanged through authentication, transfer, preparation, and swap; progress belongs to
the job. In particular, bypass the current pre-transfer `Downloading` upsert and outer
failure/cancellation upsert for this case. Only the successful finalization transaction
may replace its status, paths, bytes, policy, and timestamps. Fresh-download attempt
recording remains unchanged. Do not hold a SQLite transaction open across network/file IO.

1. Validate canonical roots and reject overlapping source/destination paths before mutations.
   Generate unique app-owned temporary and backup siblings on the destination filesystem;
   ensure local scanning ignores this staging area.
2. Prepare the payload there. Prefer a same-filesystem rename; use copy only for a recognized
   cross-device error, not every rename error. Keep source/rollback material until completion.
   Check copy completion, preserve supported entry types, and fail explicitly rather than
   silently omit unsupported entries. No old final directory is removed during preparation.
3. At a safe cancellation boundary, rename the old final directory to a backup, then install
   the prepared directory at the final path. Restore the backup if installation fails.
   Finish this short swap/rollback section before honoring a newly arriving cancellation.
4. Persist the new download state and the recovery operation's committed marker in one
   `dm-storage` transaction. If that write fails, restore the prior filesystem state
   and retain recoverable new data; the error-recording path must not overwrite the old
   usable download record. Report original and rollback errors if recovery itself fails.
5. After installation and DB recording succeed, clean app-owned backup/staging paths.
   Cleanup failure reports retained paths as a warning; it must not turn a valid installed
   download into a failed record or delete its only valid copy.

Retain the cheap same-filesystem path when possible. Cross-device preparation temporarily
needs space for both old and new content. Preserve root/ancestor/symlink guards, existing
serial-file behavior, archive-only downloads, and duplicate-work reservations.

For interruption between swap steps, keep a minimal app-owned per-work recovery record with
operation ID, work ID, validated paths, prior-record presence, and phase. Persist intent
before the first swap; record the finalization commit alongside the new download row in
the same SQLite transaction so a crash after commit but before cleanup is distinguishable
from an uncommitted swap, even when old and new paths/byte counts match. Keep this bounded
recovery metadata in `dm-storage`, not a generic durable job history. On retry, acquire the
per-work mutation guard and inspect the record, persisted work state, and actual paths before
modifying anything; phase alone is not proof a rename completed. Roll back an uncommitted
swap without rewriting the untouched old row; finish cleanup for a committed installation.
Recover only an unambiguous owned operation; retain files and
report paths when ambiguous. Do not delete directories merely because their names match a
temporary prefix, and do not promise power-loss durability without the required flushes.
Document the exact supported crash-recovery boundary during implementation.

Recovery is a precondition for every mutation of that work's download state or managed
paths, not only download retry. Add a small per-work mutation guard in `dm-library` shared
by download/finalization, removal, manual marking, and local scan/import writes. Existing
Tauri queue reservations still provide early duplicate-download feedback, but cannot be
the only protection because direct core callers and restarted apps bypass those checks.
Use one lock acquisition at each public operation boundary and private already-guarded
helpers to avoid recursive acquisition. Bulk/import processing holds only one work guard
at a time; waiting download jobs observe cancellation.

Under the guard, resolve any pending recovery before reading mutable download state or
performing the requested mutation. If ownership/paths are ambiguous or recovery/cleanup
cannot safely finish, return an explicit recovery-required result with retained paths and
do not change files or the download row on behalf of the new command. Scans/imports skip
and report such works without overwriting their rows. A successful recovery re-reads state
before deletion or marking proceeds; deletion must not report success while an owned
pending backup remains. Test restart after old-to-backup rename followed by deletion,
manual marking, and scan/import; cover committed-but-uncleaned recovery, ambiguous recovery
being blocked without mutation, and concurrent mutation requests for the same work.

Test with temporary directories and a narrow private fault-injection seam: copy failure,
install rename failure, DB write failure, rollback failure, cleanup failure, cancellation
before/after the swap boundary, destination collisions, overlapping roots, and retry after
interruption. Assert old content bytes and persisted state, not just error variants. Exercise
cross-device behavior deterministically without requiring two mounted disks in CI.
Reopen the file-backed database and a fresh Library instance after simulated interruption
before/after each rename and immediately before/after the final DB commit. Assert that
uncommitted recovery preserves the complete old row (including local path and completion
time) and bytes; committed recovery retains the new row and bytes. Also cover cancellation
before authentication and during transfer, and old/new payloads with equal byte counts.

### 4. Guard Library queries against stale responses

Assign a monotonically increasing generation to each logical product query and capture an
immutable filter/sort/page request. Accept results only if their generation is still current.

Generation changes also represent data invalidation, not just a new filter/page selection.
On download terminal events (single and bulk), tag mutation completion, and other existing
local content mutations, synchronously invalidate pending product/facet responses before
patching local state or awaiting another command. Start a fresh query for the current
selection, with clamping as needed, to reconcile content, filter membership, count, and
facets. Apply the same invalidation to an open detail request; capture work ID and request
generation so a refresh cannot overwrite another work opened meanwhile. Multiple terminal
events may coalesce refreshes, but never bypass invalidation or accept an older response.

Treat product page, total count, page clamping, facets, and loading/error state as one query
lifecycle. A page-clamp retry belongs to the same generation; do not construct it from filters
that may have changed while the request was in flight. Apply the same guard to independent
facet refreshes after tag edits. Define current-query facet failure explicitly so it cannot
silently leave facets from a previous filter selection.

Use controlled deferred promises to test A-then-B requests resolving in both orders, stale
success/error/finally paths, page-clamp retries, reset during loading, and facet refresh races.
Also test `query A starts -> download completes or tag edit succeeds -> A resolves`, with
the new authoritative query resolving both before and after A. Old product/facet/detail
responses, errors, and finally handlers must not undo the mutation, clear current loading,
or change current errors. Include detail switching during a terminal-event refresh and
download/tag changes that alter current filter membership or clamp the current page.
Keep current pagination, reload-clamping, and whole-result bulk selection behavior.

Add a small frontend unit-test command (Vitest with only the environment needed by these
controllers) and invoke it in CI. Reuse Vite/Svelte configuration where needed, without
requiring the Tauri runtime or changing the production build. Storybook checks cover the
dialog/view presentation; they do not replace async lifecycle regression tests.

## Implementation results and remaining verification

- Core auth and Tauri prompts were extracted before their behavior fixes. Cancellation now
  agrees across persisted sync/download state, bulk termination, and diagnostic job errors.
- Auth waits are cancellable; account edits share the login lock and authentication re-reads
  identity under it. Tests cover concurrent consumers, cancellation, timeout/rejection,
  remembered policy, restart, invalid/expired sessions, and validation network failure.
- Replacement preserves the old record through transfer and uses destination-side preparation,
  owned backups, and an atomic SQL update/commit marker. Recovery tests reopen SQLite around
  rename/commit boundaries, including equal-size old/new payloads. Per-work guards protect
  delete/mark/scan/import too. Manual mark/scan explicitly block/skip recovery requiring staging
  roots they were not authorized with. Partial copied data can remain at a reported retained path.
- Frontend terminal events re-query content instead of projecting failed attempt status onto
  existing downloads. Generation checks cover queries, facets, and detail requests; mutations
  invalidate prior responses. Two-factor submitting state is request-specific.
- Automated validation: workspace Rust tests with all four live gates disabled; workspace
  clippy with `-D warnings`; rustfmt; frontend Vitest/typecheck/build; Storybook build; and
  `pnpm tauri build --no-bundle`. Exact final counts/results are in `docs/work-log.md`.
- Manual/native-window and browser checks were not run (no interactive browser/native UI
  automation in this session). No existing user database was opened by launching the app.
- Live 2FA/reCAPTCHA validation requires a test account and user-entered TOTP in the app.
  It remains pending; do not treat passing local tests as proof of live authentication.
- Process interruption recovery is supported at tested boundaries. Power-loss durability,
  external concurrent filesystem mutations, cross-process writers, and automatic disposal
  of ambiguous/retained recovery files are not claimed.
