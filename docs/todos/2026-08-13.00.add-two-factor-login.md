# Add two-factor (TOTP) login support

Status: In Progress

Post-merge cancellation fixes, authentication-boundary refactoring, and regression coverage
are tracked in [Fix post-merge bugs and clarify authentication boundaries](2026-09-05.00.fix-post-merge-bugs-and-auth-boundaries.md).
The live reCAPTCHA verification below remains open independently of those fixes.

## Problem

Accounts can only be configured with a login name and password. DLsite has offered
app-based two-factor authentication (TOTP) since 2024-09-17, and an account with it enabled
cannot authenticate at all: `DlsiteClient::login` treats any credential-POST result that is
not the expected redirect chain as a hard error, so the challenge page collapses into
`UnexpectedStatus` / `InvalidCredentials`.

The goal is to show a dialog at authentication time, take the TOTP code from the user, and
complete the login with it.

## Constraints discovered

- Login runs inside every sync and download job. Both use `authenticate_account` in
  `dm-library/src/auth.rs`; remembered sessions are now persisted through `dm-credentials`.
- TOTP codes are single-use, so without session reuse a two-factor account would be prompted
  once per job, including once per queued download. Session persistence is therefore part of
  the feature, not an optimization.
- DLsite does not document the two-factor challenge. Neither the login page form
  (`login_id` / `password` / `_token` / `remember`) nor `login.dlsite.com`'s
  `assets/login/js/app.bundle.js` contains any two-factor identifier, and `/login/*` is a
  catch-all that redirects to `/auth/*` where the guessable paths 404. The contract has to be
  observed against a real two-factor-enabled account.
- The credential POST returns `302` even for wrong credentials, redirecting back to
  `/login` where the error text is rendered. A two-factor challenge is therefore likely to
  arrive as a redirect target too, not as a `200` on the POST itself — `begin_login` must
  classify by where the redirect lands, not by the POST status.

## Plan

1. **Capture the real contract.** `crates/dm-api/examples/probe_login.rs` performs the same
   credential POST as the client, follows the redirect chain, and reports each page's forms,
   form-control names, and challenge keywords, while redacting passwords and
   account-identifying values.
2. **Implement against the confirmed contract.**
   - `dm-api`: `LoginOutcome` / `TwoFactorChallenge`, `begin_login`, `complete_two_factor`,
     a shared `finish_login` extracted from `login`, and distinct errors for a rejected code
     versus an unrecognized challenge form.
   - `dm-credentials`: `CredentialRef::account_session` reusing the existing secret store.
   - `dm-library`: a single `authenticate_account` helper (restore session → validate →
     login → prompt for code → persist session) plus a `TwoFactorPrompt` trait passed
     through the sync/download request structs.
   - `src-tauri`: job-side prompt that emits `dm-two-factor-request`, waits on a oneshot with
     job cancellation and a timeout, plus `submit_two_factor_code` / `cancel_two_factor`
     commands and per-account login serialization.
   - Frontend: presentational `TwoFactorDialog.svelte` and request-specific state in
     `src/lib/controllers/two-factor-controller.svelte.ts`.

## Acceptance criteria

- [x] Probe tool can capture the two-factor challenge page contract from a live account.
- [x] Two-factor challenge is detected and a dialog collects the TOTP code.
- [x] A wrong code re-prompts instead of failing the job outright.
- [x] Cancelling the dialog cancels the owning operation with a distinct, understandable
      reason; persistence and bulk stopping use the same cancellation classification.
- [x] A successful login persists the session so later jobs, and later app runs, do not
      prompt again until the session expires.
- [x] Accounts without two-factor behave exactly as before.

Implemented and covered by unit tests. Recorded contract is in
`docs/designs/2026-08-13.00-two-factor-login.md`.

## Open, needs live verification

- **reCAPTCHA v3 enforcement.** The challenge form carries a `recaptcha_token` that the page's
  JavaScript fills from reCAPTCHA v3. A plain HTTP client cannot produce it, so the field is
  submitted empty. If DLsite enforces it server-side, code submission will fail and the flow
  needs a webview-based login instead. Unknown until tested against a real account.
- The September 5 macOS implementation session compiled/tested `src-tauri` and built the
  application with `pnpm tauri build --no-bundle`. Interactive native-window and browser QA
  remain pending; adapter/controller tests do not replace the real-account smoke test.
